# Writing Terraform for Kvindo Cloud

Written against provider `v3.1.2` (current latest release). Terraform *schemas* are exactly what
changes release to release, unlike a thin CLI — treat every field/shape claim here as something to
re-verify against the live schema if the installed version might differ (see Discovery-first below).

## The three-block shape

Every resource and data source has exactly three top-level blocks, mirroring the Kvindo Cloud API
envelope — confirmed universal across all 62 resource types via a live `terraform providers schema
-json` pull, not just a couple of examples:

- **`metadata`** — identity you set: `name`, `description`, `folder_id`, `delete_protection`,
  `labels`, and a read-only `id`.
- **`spec`** — the type-specific configuration. **Omitted for resources with no configurable fields**
  (e.g. `kvindo_folder` has `metadata`/`status` only, no `spec` — this is normal, not an error).
- **`status`** — everything the server computes: `state`, IPs, endpoints, generated credentials,
  pricing. Read-only.

```hcl
resource "kvindo_s3_bucket" "main" {
  metadata = { name = "my-app-bucket" }
  spec     = { tier = "standard", region = "ru-msk-1", quota_gib = 100 }
}
```

HCL uses **attribute** syntax (`metadata = { ... }`), never block syntax (`metadata { ... }`).

## Discovery-first: don't trust every file in this repo equally

Before writing any resource block, check its schema from a **generated, not hand-written**, source
— in order of reliability:

1. `terraform providers schema -json` against the actually-installed provider, if Terraform is
   already init'd in the working directory — the strongest ground truth, since it reads the real
   compiled schema directly.
2. `docs/resources/<type>.md` / `docs/data-sources/<type>.md` in this repo — generated by
   `tfplugindocs` from the compiled schema, so its Required/Optional/Computed tables can't drift the
   way prose can. For an external user this is the same content on
   `registry.terraform.io/providers/kvindo/kvindo/latest/docs` (pick the matching version from the
   dropdown if it might differ from what's locally installed).
3. `examples/resources/<type>/resource.tf` / `examples/data-sources/<type>/data-source.tf` — the
   per-type canonical example, the same content shown in the generated doc's "Example Usage".

**Do NOT trust `examples/s3/main.tf`, `TESTING.md`'s worked example, or `docs/index.md`'s prose
resource list as current.** Concretely verified while writing this skill: `examples/s3/main.tf` and
`TESTING.md` both still use **flat** attributes (`name = ...` directly on the resource) — the
pre-refactor shape, from before this repo moved to the `metadata`/`spec`/`status` blocks above —
while `docs/index.md`'s intro still lists "monitoring (VictoriaMetrics)" as supported even though
`kvindo_victoria_metrics` was retired in `v0.9.0`, several releases before the current `v3.1.2`. Both
are real, dated drift, not hypothetical risk — trust the generated sources (1–3 above) instead.

**Version pinning**: recommend `required_providers { kvindo = { source = "kvindo/kvindo", version =
"~> 3.1" } }` so a config doesn't silently pick up a future breaking schema change. If the installed
provider's schema and the pinned version genuinely might differ (e.g. `terraform init` hasn't run
yet against a newly-changed pin), run/re-run `terraform init` (or `-upgrade`) so what's on disk
matches the pin before trusting its schema, or check the version-specific Registry docs instead.

## Getting started in a new working directory

`terraform init` first — downloads/verifies the provider. Obvious to an experienced Terraform user,
worth stating since this skill can't assume that experience.

**A successful `terraform plan` proves nothing about credentials.** Unlike `kc` (which fails fast on
a bad token), a `plan` against empty or already-consistent state may not call the API in a way that
surfaces bad auth at all — the failure can show up for the first time at `apply`. If `apply` fails
with an auth-shaped error (401/403, "unauthorized"), cross-check the token independently before
assuming it's a Terraform-side problem — `kc login` (if the `kc` CLI and its `kvindo-cloud` skill are
available) gives a fast, unambiguous answer on whether the token itself is the issue.

## Plan before apply, always

Run `terraform plan` and show the user the diff before `terraform apply` — never
`apply -auto-approve` unprompted. This is broader than "confirm before deleting something": an
`apply` can alter or destroy resources beyond what was just written if local state has drifted, so
the confirmation gate is on *apply* generally.

**State is not disposable.** Never run `terraform state rm`, `terraform taint`, `-target`, or
hand-edit `.tfstate` without the user explicitly asking for it — these rewrite what Terraform
believes is real (or narrow what an apply touches) without the normal plan-diff visibility, and a
mistake here is much harder to notice than a bad `apply`. This is the *default* case, not just a
reaction to failure: an ordinary multi-resource `apply` where one resource errors partway through is
already handled correctly by Terraform's own state tracking — whatever succeeded is recorded,
whatever didn't stays pending — so normal recovery is simply "fix the cause shown in the error, run
`apply` again" (idempotent), not state surgery. `kvindo_transaction` is additionally atomic at the
API level per the README ("all succeed or all roll back") — a sub-resource of a transaction can't
independently succeed/fail; the whole transaction either lands or it doesn't. (This specific claim is
taken from the README, not independently verified by reading the transaction resource's own source —
if a transaction ever looks partially applied in state, that contradicts the documented guarantee and
is worth flagging as an anomaly, not resolving via state surgery.)

## State is a plaintext secrets store

Every `status` field lands in state as-is, which for these resources includes real secrets: S3
access/secret keys, user tokens, kubeconfigs, the VM Windows administrator password, VPN configs.
Never commit `.tfstate`/`.tfstate.backup` (confirm `.gitignore` covers it before the first apply in a
new repo); for anything beyond a throwaway local experiment, a remote backend with encryption at
rest is the right default, not local state.

**`sensitive = true` controls *where* a value can appear, not whether it exists in plaintext
somewhere.** It redacts the value from the `plan`/`apply` diff and from a bare `terraform output`
listing — it does **not** remove the plaintext from state, and running `terraform output <name>` for
that *specific* output (or `-json`) still prints the raw value. Never run either form yourself and
paste the result into the conversation — if the user genuinely needs the value, tell them the command
to run themselves in their own terminal rather than relaying it back through Claude. Mark any output
of a secret-bearing `status` field `sensitive = true`: `access_key`/`secret_key` (`kvindo_s3_user`),
`token` (`kvindo_user_token`), `kubeconfig` (`kvindo_kubernetes_user`),
`windows_administrator_password` (`kvindo_vm`), `config` (`kvindo_open_vpn_user`).

## Interrupted-apply recovery

If a 30-minute provisioning poll times out mid-flight, `terraform import <type>.<name>
<resource-id>` the now-real resource instead of re-running `apply` (which would try to create a
duplicate). Finding the ID: check the Kvindo Cloud console, or — since the resource was actually
created server-side — `kc get <type> -A -o json | jq` by name if the `kc` CLI and its `kvindo-cloud`
skill are available (the two skills compose here). **Before importing, run `terraform state list`
and confirm that ID isn't already bound to a different resource address** — importing the same real
resource under two addresses makes the next `apply` treat one as "keep" and the other as "shouldn't
exist, destroy," and it's genuinely ambiguous which wins without checking first. After importing, run
`terraform plan` again rather than assuming a clean import — a residual diff means the config doesn't
yet exactly match what was actually created.

## A verified provider quirk — don't "fix" it via state surgery

The README's design notes claim write-only fields (e.g. `root_password` on
`kvindo_postgresql_standalone`) are kept plain `Optional` specifically because the API never echoes
them back. **Checked directly against the live schema** (`terraform providers schema -json`):
`root_password` is actually `optional: true, computed: true` — Optional+Computed, not plain Optional
— and its response-read path returns `null` for a field the API doesn't send back. Combined, this
means: set it once in config, `apply` succeeds, but state ends up holding `null` for that field — and
since `UseStateForUnknown`-style suppression only applies when the *planned* value is unknown (i.e.
omitted from config), an explicitly-set `root_password` will show as "changed" on every subsequent
`plan`, indefinitely. **If a user sees this kind of field "changing" every plan despite an unchanged
config, that's this known quirk, not real drift** — don't resolve it with `terraform state
rm`/hand-editing state; it's a provider-side inconsistency between design intent and actual schema,
out of scope for this skill to fix. The standard Terraform answer to a field that will never stop
showing a spurious diff is a `lifecycle { ignore_changes = [...] }` block (e.g. `ignore_changes =
[spec.root_password]`) — offer that as the practical workaround if it's actually bothering the user.

## Other things that are working as intended, not bugs

`status.state` is deliberately `(known after apply)` while a resource is still provisioning and only
freezes once `stable` (a terminal-gated plan modifier — avoids both a stale frozen value and a
permanent diff).

**IDs are client-generated ULIDs**, not server-assigned — the opposite of how most Terraform
providers' resource IDs work. This is what lets a `kvindo_transaction` cross-reference a sub-resource
before the API has created it: pre-assign the producer's `metadata.id` (a ULID you generate) and
reference that same value in the consumer's `spec` within the same transaction.

## Resources vs. data sources

A `resource "kvindo_x"` block creates/manages/destroys that thing; a `data "kvindo_x"` block only
looks up something that already exists (by ID) without touching it — use a data source when
referencing infrastructure Terraform shouldn't own or recreate. Not every resource type has a
matching data source (`kvindo_transaction` doesn't) — check `docs/data-sources/` or the
`examples/data-sources/` listing rather than assuming one exists.

## Practical gotchas

S3 bucket names are globally unique across every Kvindo Cloud customer, not just within your own
account → always suffix with `random_id`:

```hcl
resource "random_id" "suffix" { byte_length = 4 }

resource "kvindo_s3_bucket" "main" {
  metadata = { name = "my-app-bucket-${random_id.suffix.hex}" }
  spec     = { tier = "standard", region = "ru-msk-1", quota_gib = 100 }
}
```
